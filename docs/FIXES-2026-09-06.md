## 1. Direct Account Replacement Worker Race

**Disposition:** Accepted limitation for the current product. Reopen before adding direct account switching.

### Current Risk

Room contains one shared movie dataset without account ownership metadata. During an account transition, Firebase Auth can already expose account B while Room still contains account A data and `MainActivityViewModel` is clearing it.

An existing periodic, immediate, or per-movie WorkManager job can then:

1. Read B as the current authenticated UID.
2. Read A's remaining movie snapshot from Room.
3. Pass the current-Auth check for B.
4. Upload A's data to B's Firestore path.

Relevant code:

- `app/src/main/java/com/asensiodev/santoro/MainActivityViewModel.kt`
- `core/sync/src/main/java/com/asensiodev/santoro/core/sync/worker/SyncWorker.kt`
- `core/sync/src/main/java/com/asensiodev/santoro/core/sync/worker/UploadWorker.kt`
- `core/sync/src/main/java/com/asensiodev/santoro/core/sync/data/repository/DefaultSyncRepository.kt`
- `core/sync/src/main/java/com/asensiodev/santoro/core/sync/scheduler/WorkManagerSyncScheduler.kt`

### Product Decision

Santoro does not expose a direct authenticated `A -> B` transition. Supported account changes pass through `A -> null -> Login -> B`: the first cleanup finishes before Login is published and the later login clears Room again. Anonymous account collision also signs out before a later explicit login, while Google linking preserves the same UID.

The race therefore requires an unsupported direct Auth replacement, future account-switching UI, another component signing in while already authenticated, or externally manipulated state. Movie history and watchlist contamination would have meaningful privacy impact, but the current reachability is too low to justify restoring owner columns, schema 6, per-user databases, generations, or an outbox.

FIP-023 may ship without additional ownership infrastructure. Direct account replacement is not a supported product guarantee.

### Required Before Supporting Direct Account Replacement

- Sync must not read a local upload candidate until the active app session has established authority over the shared Room dataset.
- The same authority must be checked again immediately before each Firestore write boundary.
- Account deletion marker and lease checks must remain effective.
- Cancellation must continue to propagate.
- Normal same-UID process recreation must retain its current inexpensive path.

The implementation approach must be decided before coding. Possible approaches include a shared session-readiness authority or serialization of session preparation and sync snapshot acquisition. Current Auth alone is not sufficient because it identifies the remote destination, not the owner of unpartitioned Room contents.

### Future Tests

- Auth is B, Room still contains A data, cleanup is blocked, and a full-snapshot worker starts: no Room snapshot is uploaded.
- Auth is B, Room still contains A data, cleanup is blocked, and a per-movie worker starts: no movie is uploaded.
- Cleanup succeeds and B becomes authoritative: sync can proceed for B.
- Auth changes while a snapshot or chunked upload is running: no later Firestore boundary is crossed.
- Cancellation while waiting for session authority propagates.
- Account deletion marker or lease remains a terminal no-op for queued work.

## 2. Recompute Guest Onboarding After Preferences Load

**Status:** Fixed and covered.

### Current Risk

`MainActivityViewModel` initializes `hasSeenGuestOnboarding` with `false` and samples its current value when publishing an authenticated session. If Firebase Auth emits an anonymous user before the persisted onboarding preference emits `true`, the onboarding sheet is shown again. The later preference emission does not currently recompute `uiState`.

Relevant code:

- `app/src/main/java/com/asensiodev/santoro/MainActivityViewModel.kt`
- `app/src/test/java/com/asensiodev/santoro/MainActivityViewModelTest.kt`

### Required Outcome

- Persisted onboarding state must participate reactively in the authenticated UI state.
- A returning anonymous user who already dismissed onboarding must not see it again, regardless of Auth and preference emission order.
- Dismissing onboarding must continue to hide it immediately and persist the choice.
- Onboarding preference updates must not trigger session cleanup or duplicate sync scheduling.

### Required Tests

- Anonymous Auth emits before persisted `hasSeenGuestOnboarding = true`: onboarding becomes hidden after preferences load without restarting the session.
- Persisted state emits before anonymous Auth: onboarding remains hidden.
- New anonymous user with `hasSeenGuestOnboarding = false`: onboarding is shown.
- Dismissal updates UI immediately and persists `true` exactly once.
- Preference emissions for the same UID do not clear Room or reschedule sync.

Current coverage verifies delayed persisted state, immediate dismissal, no Room cleanup, and no duplicate sync scheduling. Existing session construction covers the initial persisted-state value.
